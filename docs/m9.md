# Milestone 9 — planner, digest, adapter for other agents

Date: 2026-11-21. Host: Linux x86_64. Everything below was run unless it is
under **Not verified**.

## What exists

- **Planner.** A person's plan is their own tasks plus the inbox items
  triage placed under `prepare` (events and deadlines ahead). Entries are
  grouped as overdue, next 24 hours, this week, later and no date. Any
  inbox item can be turned into a task ("Plan"); it is then listed once.
  Tasks are personal. The sidebar shows how many are overdue or due within
  a day.
  - API: `GET/POST /api/planner`, `POST/DELETE /api/planner/<id>`.
  - CLI: `almighty plan`, `plan add <title> [--in-days N]`, `plan done <id>`,
    `plan rm <id>`.
- **Digest.** What arrived that needs nothing from the person (`fyi`),
  grouped by source and thread, largest group first, with the people
  involved and the newest titles. It never raises a notification. On
  request the operator's model writes it out in the person's language; only
  titles are sent.
  - API: `GET /api/digest?hours=N`, `POST /api/digest/summary`.
  - CLI: `almighty digest [--hours N] [--written]`. Client: "Digest" tab in
    the inbox.
- **Other agent runtimes.** `almighty acp -- <agent command>` is a client
  for the Agent Client Protocol (JSON-RPC over the agent's stdio). It reads
  prompts from the terminal, prints the agent's text, plans and tool calls,
  and puts permission requests to the person (`--permissions ask | deny |
  allow`; "always" options are never chosen for them). Run inside an
  almighty session (`almighty run -- almighty acp -- <agent>`) the agent is
  a normal terminal in every client and its tool calls are recorded with the
  session's events. The adapter offers the agent no file or terminal access
  of its own.

## Verified

- Automated (`cargo test --workspace`, 55 tests): tasks (owner only, done
  and reopen, dates, limits on titles); the plan's order and counts; an
  event from the inbox appearing by itself and once when turned into a
  task; the digest's grouping and what it leaves out; the written digest
  through a stand-in provider (only digest titles sent, 503 without a
  provider); the ACP client against a built-in stand-in agent: a full
  prompt turn (plan, tool call, permission, message), refusal by policy and
  when nobody can be asked, a clear error for a request the client does not
  offer, and for a program that is not an agent.
- By hand: `plan add`, `plan`, `digest` on a scratch server with 100 real
  pull requests; the ACP client inside a session, with its tool calls in the
  session's events.
- Desktop client in the headless container: the plan with its sections,
  ticking a task, adding one from the form, the digest tab with two groups.

## Not verified

- A real ACP agent: none is installed here. The message shapes follow the
  protocol's public documentation (version 1); `session/request_permission`
  and the stdio framing in particular were written from the documentation
  and from memory, not from a running agent.
- Web client and phone layout of the planner and digest (compiled only);
  Windows and macOS.
- The written digest with a real model.

## Not built from the brief

- Dates are calendar days in UTC; no time of day, no time zone, no
  recurring tasks, no reminders for tasks (only inbox items notify).
- Calendar connectors: nothing emits events with `due` yet, so the
  "prepare" path is fed by hand or by a future plugin.
- Team, organisation and tech-news feeds for the digest need their own
  connectors (RSS, for instance).
- The ACP adapter does not map the agent's sub-sessions to the agent tree,
  does not load earlier sessions, and does not pass MCP servers to the
  agent.
