# Milestone 8 — identity provider sign-in, roles, install skills

Date: 2026-11-21. Host: Linux x86_64. Everything below was run unless it is
under **Not verified**.

## What exists

- **Sign-in through an OpenID Connect provider** (`[oidc]` in
  `workspace.toml`): authorization code flow with PKCE, state and nonce.
  The id token is checked for signature (asymmetric algorithms only, keys
  from the provider's JWKS), issuer, audience, expiry and nonce; the email
  must be verified and, if the operator lists domains, belong to one.
  - The person's account is created on first sign-in, named after their
    email, with no usable password. It is tied to the provider's subject,
    so a changed email does not create a second account.
  - An empty workspace can only be claimed by an address on the `admins`
    list (it becomes the owner). The list promotes on later sign-ins and
    never demotes: roles are managed in almighty.
  - A local account with the same name is not linked silently
    (`link_existing = true` allows it).
  - The session token never travels in a URL: the client is sent back with
    a one-time code (valid 60 s) that it trades for the token. Clients may
    only be sent back to a loopback address or to `redirect_urls`.
- **Clients.** CLI: `almighty login --sso` (prints the address to open and
  waits on a loopback port). Desktop: "Sign in with your organization"
  opens the system browser and waits the same way. Web: the same button
  leaves for the provider and comes back to the page. Phones: not yet.
- **Roles.** `POST /api/users/<name>/role` and `DELETE /api/users/<name>`,
  `almighty user role | remove`. Admins manage members and guests; only
  owners touch admins and owners; the last owner cannot be demoted or
  removed; nobody removes themselves. Removing a person ends their sessions
  at once. Changes go to the audit log.
- **Web client from the server.** With `ALMIGHTY_WEB_DIR` set, the server
  serves the built web client at `/`, so one address carries the app and
  its API.
- **Install skills** in `skills/`: personal, server (reverse proxy, TLS,
  backups, alias host redirect) and company (identity provider, roles,
  shared-server rules), each with checks to run before finishing.

## Verified

- Automated (`cargo test --workspace`, 49 tests): the whole sign-in
  against a stand-in provider that signs real RS256 tokens — first owner
  from the admin list, later members, the one-time code used once, and
  seven refusals (another domain, unverified email, a token from another
  sign-in, another audience, expired, signed with the public key as an
  HS256 secret, failed PKCE exchange); replayed and made-up states;
  redirect allow-list; account creation, linking and promotion; role rules
  through the API; a removed person's token stops working.
- By hand: `almighty login --sso` end to end against a second stand-in
  provider written separately (Python, tokens signed with `openssl`), for
  an owner and a member; `almighty user role` refused for a member.
- Web client in Chromium, served by the server itself through
  `ALMIGHTY_WEB_DIR` (debug build): the page talks to its own origin, the
  "Sign in with your organization" button goes to the provider and comes
  back signed in, and the code is removed from the address bar. Unknown
  `/api/` paths answer with an error, other paths with the app.

## Not verified

- A real provider (Okta, Entra, Google Workspace, Keycloak). Differences
  to expect: claim names for the email, `email_verified` missing (Entra),
  issuer formats with a tenant id.
- The desktop button (same loopback approach as the CLI, compiled only).
- A release build of the web client behind a reverse proxy; the install
  skills were written, not executed.
- Windows and macOS.

## Open points

- No TOTP for local accounts yet (the brief lists it as optional).
- No single logout and no periodic re-check with the provider: a session
  lasts 30 days unless the person is removed in almighty.
- Groups from the provider are not mapped to roles.
- Device tokens are not in the OS keychain: the CLI keeps them in a 0600
  file, the desktop client in its settings file.
