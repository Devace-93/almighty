# Milestone 1 — accounts, tokens, permissions, push channel

Date: 2026-11-20. Verified on Linux unless marked otherwise.

## What exists

- **Storage**: one SQLite file (`rusqlite`, bundled) with users, tokens and an
  audit log. Created with mode 0600. Terminal sessions stay in memory.
- **Accounts**: users with a role (`owner` > `admin` > `member` > `guest`).
  Passwords are hashed with Argon2id; at least 10 characters.
- **First run**: the server prints a one-time setup code. `POST /api/setup`
  with that code creates the owner, once. `almighty user add` does the same
  locally, straight into the database.
- **Tokens** (random 256-bit, stored as SHA-256):
  - `login`: from name + password, 30 days.
  - `api`: long-lived, for scripts and MCP clients; shown once, revocable.
  - `agent`: one per terminal session, placed in that session's environment
    as `ALMIGHTY_TOKEN`; deleted when the session is closed and at server
    start.
- **Login throttling**: five failures for a name lock it for a minute.
- **Who can do what**
  - Guests read. Members and above create, type, resize, close, lock, grant.
  - Admins list and create users and read the audit log; only an owner can
    create another owner.
  - An agent (the process inside session S, using S's token) can read S,
    fully control sessions it started, and reach other sessions only through
    a grant (`read` or `write`) given by a person. Sessions it may not see
    answer 404.
  - Agents cannot lock, grant, manage accounts or create tokens, and can
    report hooks only for their own session.
  - Who typed is decided by the token, not by the request: people set the
    human-priority window, agents are subject to it and to locks.
- **Audit log**: logins, session create/close, lock, grants, and every agent
  input (text and key names).
- **Push channel**: `GET /api/events` (WebSocket) says when the session list
  or an agent tree changed; clients refetch. Polling remains as a 10 s
  safety net.
- **CLI**: `setup`, `login`, `logout`, `whoami`, `user add|list`,
  `token create|list|revoke`, `grant`. Tokens are saved per server URL in
  the user's config directory (0600). Inside a session the CLI and the MCP
  server act as that session's agent automatically.
- **Claude Code**: `almighty run -- claude` now also passes `--mcp-config`
  with the `almighty mcp` server, so the agent gets the terminal tools.
- **Clients**: sign-in / first-run screen, several workspaces with a
  switcher, sign out, read-only indicator. The workspace list is stored in
  localStorage (browser) or a 0600 file (desktop).

## Verified

- 14 server tests, including an in-process API suite for setup, login,
  lockout, token lifecycle, roles, agent isolation, grants, locks and audit;
  5 client tests.
- CLI end to end on a scratch server: setup, whoami, run, term, attach from
  tmux, API token, local `user add`, guest login refused on input.
- Claude Code 2.1.329 inside a session, through MCP: created its own
  terminal, typed and waited in it, saw only its own sessions, and got
  "no session s1" for a session started by a person. The audit log recorded
  its inputs.
- Desktop client (headless container): wrong password message, sign in,
  terminal over an authenticated WebSocket, typing, a session created from
  the CLI appeared without a refresh.
- Web client: signed in as a guest, saw the read-only tag.
- Android: builds. Sign-in on the emulator **not run**.

## Limits and open points

- WebSockets from browsers carry the token in the query string, so it can
  end up in proxy logs. A first-message handshake would avoid that.
- The desktop and CLI token files are plain files with private permissions,
  not the OS keychain. Phones do not persist the workspace list yet.
- No TLS in the server: for anything beyond loopback, put it behind a
  reverse proxy with HTTPS. The server still refuses nothing by address.
- No OIDC yet, no password change, no user removal, no role change, no TOTP.
- One workspace per server. Sessions are visible to every signed-in person;
  there is no per-user privacy between members of a workspace.
- Sessions started by an agent keep running after the agent's session ends.
- Windows: not built or run with these changes yet (`rusqlite` bundled
  needs a C compiler).
- Form fields in the native clients are uncontrolled on purpose: a
  controlled field dropped characters under fast typing.
