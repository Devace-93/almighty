# Milestone 6 — service plugins (almighty's side)

Date: 2026-11-21. Host: Linux x86_64. Everything below was run unless it is
under **Not verified**.

The five 3m4 apps (flows, crew, sketch, blueprint, trace) are briefs today,
not running programs. This milestone builds what almighty needs to host
them and tests it against a stand-in service.

## What exists

- **Manifest** `kind = "service"`: base URL, web panels, resource types,
  permissions (`items = ["write"]`, `events = [...]`). No component, no
  code of the service runs inside the server or inside the client's page.
- **Install** with `almighty plugin add <dir>`: same approval as light
  plugins. The event secret is printed once.
- **Pages.** A web panel opens the service's page in the side browser, with
  a five-minute identity token in the URL fragment.
- **Identity.** Tokens are JWTs signed with an Ed25519 key the workspace
  creates on first use (`signing.key`, mode 0600); the public key is served
  at `/.well-known/jwks.json`. Claims: issuer, audience (the plugin),
  user, role, workspace, expiry.
- **Events in**: `POST /hooks/<plugin>` checked with HMAC-SHA256 over the
  body, deduplicated by event id, optionally creating an inbox item (which
  then goes through triage). Wrong signature, unknown plugin and disabled
  plugin all get the same `401`.
- **Events out**: services that list `item.created` / `item.updated` get a
  signed POST with the light version of the item; three attempts.
- **Resource links**: `3m4://<type>/<id>[@version]` resolves to the page of
  the plugin that registered the type.
- **Manifests** for the five apps in `plugins/3m4/`.
- Protocol details are in `PLUGINS.md` → "Service plugins".

## Verified

- Automated (`cargo test --workspace`, 43 tests): manifest rules (paths
  must stay on the service, panel types per plugin kind, event names);
  install without a component, secret shown once and hidden from listings;
  tokens verified with the published key only; resource links and rejected
  malformed ones; inbound events (missing, wrong and mismatched signatures,
  unknown plugin, missing id, duplicate, item creation reaching the inbox,
  permission required, disabled plugin); outbound delivery with a valid
  signature, only subscribed event types, no echo of the plugin's own
  items, no item body; every manifest shipped in `plugins/` parses.
- Desktop client in the headless container: panels of two service plugins
  in the sidebar; opening one loads the stand-in page in the side browser
  and the page reads the signed token (user, role, audience).

## Not verified

- Any of the five real apps: they are not built. The manifests follow the
  platform contract's ports and paths and may need changes.
- Verification of the token by an independent JWT library (the test uses
  the same Ed25519 crate that signs).
- Web client (compiled only), Windows, macOS.

## Open points

- The token is visible in the side browser's address bar for its five
  minutes. A handshake over postMessage would hide it, but needs the
  embedding protocol (not built) and a different approach on desktop, where
  the page lives in a separate native webview.
- Outbound events are not queued on disk: a service that is down for longer
  than the three attempts misses them.
- A service's MCP endpoint is listed, not proxied: people still add it to
  their agent's MCP configuration themselves.
- `http://` base URLs are accepted (local development); a deployment across
  machines should use `https://`.
