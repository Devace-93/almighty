# Milestone 4 — inbox and triage

Date: 2026-11-21. Host: Linux x86_64. Everything below was run unless it is
under **Not verified**.

## What exists

- **Inbox.** Every item a connector emits is sorted, per person, into
  `reply`, `act`, `prepare`, `fyi` or `noise`, with a priority 0–3, a short
  summary and the reason for the decision. People with the `member` role or
  higher have an inbox; guests and agents do not.
- **Rules** (always on, nothing leaves the server): muted people and
  sources, noise and urgent keywords, important people, items addressed to
  the person (`direct`, or a mention of one of their `me` handles), dates
  ahead, and what the person taught by moving items.
- **Preferences** live in `users/<name>/triage.toml` (all optional):

  ```toml
  input_language = "es"       # language of summaries
  output_language = "match"   # language of draft replies
  me = ["my-handle"]
  [people]
  important = ["lead"]
  muted = ["bot"]
  [sources]
  muted = ["owner/noisy-repo"]
  fyi = ["#announcements"]
  [keywords]
  urgent = ["outage"]
  noise = ["newsletter"]
  [notify]
  min_priority = 2            # 4 turns notifications off
  quiet_hours = "22:00-07:00"
  utc_offset_minutes = -360
  ```

  A file that does not parse is reported by `almighty inbox preferences`.
- **Corrections.** Moving an item or changing its priority is stored and
  kept even when the item is updated. After two moves of items with the same
  source, kind and sender, new ones like them go to that bucket. The last
  twelve moves are also given to the model as examples.
- **Model step (optional).** `[triage]` in `workspace.toml` chooses a
  provider: `anthropic` (Messages API over HTTPS; the key is read from the
  environment variable named in `api_key_env`, default model
  `claude-opus-5-5`, effort `low`, refusal fallbacks on) or `command` (any
  local program: prompt on stdin, JSON on stdout). The model may change
  bucket and priority and writes the summary and a draft reply in the
  preferred languages. Its answer is validated; on any failure the
  rule-based result stays. Items from muted people or sources are never
  sent. With no provider, item content never leaves the server.
- **Notifications.** When an item lands in `reply`, `act` or `prepare` at
  or above the person's threshold and outside quiet hours, the server pushes
  a notification event to that person only (title and summary, once per
  item); the desktop client shows a system notification, the web client a
  browser one after asking for permission.
- **Client.** "Inbox" in the sidebar with the count of items that want
  something; tabs per bucket, move, priority, snooze one day, done/reopen,
  the draft and the reason. Lists refresh when the server reports a change.
- **CLI.** `almighty inbox [--bucket … --show open|done|all]`, `inbox move`,
  `priority`, `done [--undo]`, `snooze`, `preferences`.
- **Connectors** (light plugins, HTTPS only):
  - `plugins/slack`: messages of the conversations the token's owner is in;
    direct messages and mentions are marked as addressed to them.
  - `plugins/gmail`: recent inbox mail through the Gmail API (sender,
    subject, snippet); bulk mail is not marked as addressed to you; read
    mail counts as done. The access token is requested on every sync and
    not stored.
  - `plugins/github` now marks review requests as addressed to you.
- Plugin secrets are now encrypted at rest (`secret.key`).

## Verified

- Automated (`cargo test --workspace`, 32 tests): every rule and its
  precedence; per-person results; filters; learning after two moves, for
  that person only; done, snooze and reopen; a person's choice surviving an
  update; closed items; a broken preferences file; notification thresholds,
  once-per-item, quiet hours, guests excluded; the model step against a
  stand-in provider (request shape, headers, language preference, muted
  senders never sent, provider error / refusal / non-JSON answers leaving
  the rules in place); the command provider; the Slack and Gmail connectors
  against stand-in APIs (hints, skipped messages, incremental sync, missing
  or refused credentials).
- By hand: 50 real pull requests triaged with keyword and important-person
  preferences; `inbox move`, `priority`, `--bucket`, `--show done`.
- Desktop client in the headless container: inbox tabs with counts, an
  entry with its reason, "Done" removing it and the sidebar count updating,
  the FYI tab.

## Not verified

- Slack and Gmail against the real services: no accounts were used. The
  request shapes come from their public documentation and may need fixes.
- The Anthropic provider against the real API (no key was used), and the
  quality of model-made triage, summaries, translations and drafts.
- System notifications on screen (the container has no notification
  service); web notifications; Windows and macOS.
- Inbox on a phone-sized screen and in the web client (compiled only).

## Known limits and open points

- No IMAP: light plugins only speak HTTPS. Options: a socket capability for
  plugins, or a built-in IMAP connector.
- Connector credentials are per workspace, so today one Slack or Gmail
  account feeds every member's inbox. Per-person connector accounts are
  needed before a team uses this.
- No inbound webhooks yet (`POST /hooks/<connector>`); connectors poll.
- Quiet hours use a fixed UTC offset, not a time zone with daylight saving.
- Triage re-reads up to 500 recent items per request; fine for one person,
  to be indexed before large inboxes.
- The model step runs once per item version and is not retried after a
  provider error.
- "Awareness" digests and planner entries from `prepare` items belong to
  milestone 9.
